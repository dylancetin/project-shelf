# Agent Servers MCP

Project Shelf exposes preview-server and registered-project tools at `http://beelinkk:4958/mcp`, using `@hono/mcp` and the official MCP SDK. See [the installed agent skill](../skills/project-shelf-agent-servers/SKILL.md) for client configuration, inputs, outputs, examples, retry behavior, and required preview workflow.

| Tool | Inputs | Result / behavior |
| --- | --- | --- |
| `add` | `name`, `cwd`, `command`, `threadId`, optional `idempotencyKey` | Start or reuse an independently retained agent preview owned by the caller's T3 Code thread (`T3CODE_THREAD_ID`). |
| `restart` | `id` | Stop the agent preview's whole process tree, then rerun the same command in the same `cwd` on the same port; returns the `add` result shape with the same ID and URL. |
| `delete` | `id` | Stop the agent preview's process tree, then remove its registration. |
| `projects_list` | `{}` | `{ projects: Project[] }`, matching `/api/projects`, including service links, hidden entries, saved commands, and current managed runtime state. |
| `project_run` | `id`, optional `mode` (`dev`, `build`, `prod`; defaults to `dev`) | `{ project: Project }`; start the registered project's saved command through the same process manager and mutation lock as the dashboard. |
| `project_logs` | `id` | `{ logs: LogLine[] }`, matching `/api/projects/:id/logs`, with line IDs, timestamps, and stdout/stderr/system streams. |

The same-origin UI restarts a preview with `POST /api/agent-servers/<id>/restart`, which runs the `restart` operation above and returns `{ server }`. Use an ID from `projects_list` for the project tools. `project_run` returns immediately after starting; poll `projects_list` and `project_logs` for completion or failure. `build` runs only the build command; `prod` first runs the configured build command, and a failed build prevents production from starting. Services, missing commands, unknown IDs, and already-active projects return MCP tool errors. Stop existing runs through the dashboard before rerunning. Project runs use their configured port and stop on panel shutdown; their in-memory logs default to the last 500 lines of at most 4000 characters each and are cleared on restart. An unstarted registration has an empty log array. Listing and reading logs never start commands or scan directories.

The credential is generated on startup at `${PANEL_DB_PATH}.mcp.json` (default `data/panel.sqlite.mcp.json`, mode 0600). This ignored local file contains `bearerToken`; load it into a local MCP client Authorization header, never commit or share it. To rotate, stop the panel, remove **only this credential file**, restart, and update clients. No global configuration is changed. Requests require a configured Host, no cross-origin browser requests, and a matching bearer token. For agent previews, the same-origin UI may list/read logs and stop runs, but cannot launch arbitrary commands. No unauthenticated agent-preview launch API is added. MCP resources provide authenticated read access for agent clients.

## Cloudflare tunnels

The same-origin UI can open a [Cloudflare quick tunnel](https://try.cloudflare.com) to a ready preview with `POST /api/agent-servers/<id>/tunnel` and close it with `DELETE /api/agent-servers/<id>/tunnel`. The POST resolves once `cloudflared` reports a public `https://*.trycloudflare.com` address and a registered edge connection (45-second limit). The tunnel connects to `http://127.0.0.1:<port>` with the Host header rewritten to `localhost`; it survives `restart` (same port) and is always closed when the preview is deleted, by Stop, `delete`, or settled-thread removal. Listings include the open tunnel as `tunnel` (`null` when closed). Tunnels are in-memory panel child processes and close when the panel stops. Registered projects use `POST`/`DELETE /api/projects/<id>/tunnel` the same way while their development or production command is running.

## Lifecycle and ownership

Separate SQLite `agent_servers` and `agent_server_requests` tables preserve records and idempotency tombstones; existing Projects are unchanged. The initial persisted local machine identity is structured for future multi-host support; currently all commands execute on beelinkk only. No arbitrary PID/unit adoption or remote execution exists.

Each record's generated UUID determines `project-shelf-agent-<UUID>.service`. `systemd-run --user` creates an independent transient unit, outside the panel service's control group. Before reading/stopping a loaded unit, its Description must match the persisted server and machine identity. Stop uses systemd's bounded graceful termination followed by SIGKILL for the entire control group, verifies no processes remain, then deletes the record. A failed stop leaves it visible. Preview units survive a panel restart but not a machine reboot; missing units appear stopped. They do not autostart on reconciliation. `restart` relaunches a record in place under the same allocation lock as `add`/`delete`: it stops the current unit with the same verification as delete (a failed stop starts nothing), checks the persisted port is free, then starts the same command, `cwd`, unit name, and port. If another program took the port while the preview was down, it is not killed; the record stays stopped with a `Restart blocked` diagnostic, and the caller should delete it and add a new preview. A start failure is recorded as `Restart failed`, and a later successful restart clears it. To change the command or `cwd`, delete and add instead. Successful commands that exit are retained as stopped; failed units remain available for diagnostics.

## T3 Code thread ownership

`add` requires `threadId`, the caller's `T3CODE_THREAD_ID` environment variable. Project Shelf verifies it against T3 Code's thread projection, opened **read-only** from `${PANEL_T3_HOME}/userdata/statev2.sqlite` (default `/home/taytay/.t3-nightly`); it never writes to T3 Code's database. An unknown thread is rejected with 400, a thread whose top-level thread is already inactive with 409, and unreadable T3 state with 503. The thread is part of the idempotency fingerprint, so identical inputs from another thread start a separate preview rather than sharing one it would later remove.

The **top-level thread** governs the preview: subagent links are climbed to the parent thread you're using, so a delegated task finishing (and being auto-settled) does not stop it. A fork is its own thread even though T3 Code records its original as the lineage root. Following T3 Code's own rule for abandoned subagent work, the thread is inactive when it is settled (`settledOverride = 'settled'`), archived, or deleted.

The production server checks every 10 minutes (`agentThreadCheckMs`; disabled in `createApp` unless set). Each inactive thread's previews are **fully deleted**, exactly like Stop/`delete`: the whole control group is stopped and verified, the record is removed, and its idempotency key is tombstoned (use a new key to start another). A failed stop keeps the record and is retried at the next check. Checks never overlap and are logged to the panel journal. A missing thread, unreadable T3 state, or a record created before thread ownership (no `threadId`) is never removed automatically. Records and UI rows include `thread` with the starting `id`, governing `rootId`, `title`, `status` (`active`, `settled`, `archived`, `deleted`, `missing`, `unavailable`), and a desktop deep link `t3code://threads/<environmentId>/<rootId>`; the environment ID comes from `${PANEL_T3_HOME}/userdata/environment-id`.

## Ports and environment

Ports are randomly allocated from 5000–5999. Allocation is serialized in-process, reserved with a unique database port index and an IPv6 dual-stack listening socket during registration. The reservation is released immediately before systemd starts the command; external programs can still race to bind, so readiness additionally checks `/proc` socket ownership against the unit cgroup before and after IPv4 HTTP, requiring an owned IPv4 wildcard listener (`0.0.0.0`). An IPv6-only wildcard socket is not proof of ownership of the IPv4 probe. It never kills port occupants. Use `{port}` with tools ignoring `PORT`, strict-port mode, and host `0.0.0.0`; no flags are appended automatically. Visit URLs honor the preferred hostname; the empty “Original hostname” preference falls back to the persisted local machine hostname.

Child environment is cleared with `env -i` and rebuilt from PATH, HOME, USER, LOGNAME, LANG, LC_ALL, TMPDIR and assigned PORT only. Both panel and user-manager secrets are excluded. Commands are arbitrary user-trusted code, not sandboxed: a bearer client has the same OS-user authority as the panel. Protect the token and use trusted networks/TLS. Readiness proves local ownership and HTTP, not remote firewall reachability; listen on all interfaces for remote Visit.

Logs go to the journal, survive panel restarts, and retain timestamps and stdout/stderr distinction (`systemd-cat` assigns separate stream priorities with level-prefix parsing disabled). Unit output is rate limited (200 messages/30 seconds); reads return at most 150 recent lines/64 KiB. On-disk retention is bounded by the host's journald quotas (system defaults if not customized), not an unbounded application log file. Journal rotation may remove older output; no unrelated global journald configuration is changed.

The UI is shared with the browser extension, which proxies only the explicit list/log/stop API paths and never receives the MCP bearer token. After building the extension, use the SCP/reload instructions in the main README; do not reinstall or change its folder.
